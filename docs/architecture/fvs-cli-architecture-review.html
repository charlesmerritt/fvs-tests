Architecture approved Serial first Python + DuckDB Containers later

One CLI for many FVS engines

Select a named example, execute it through a chosen engine, retain every artifact, and compare SQLite outputs against a known baseline with declared tolerances. 

fvs-test run --engine fvsjl --example thinba
fvs-test compare --example thinba --actual .runs/<run-id>/FVSOut.db

Decision

Three viable boundaries

A. Typed adapters

Selected

Small Python adapter per engine behind one stable protocol. Examples remain engine-neutral manifests.

  • Best diagnostics and engine-specific validation.
  • Easy to unit-test without launching real engines.
  • Adapters can later gain containers or remote execution without changing the CLI.
Cost: each new engine needs a small Python class.

B. Command templates

Describe each engine as shell arguments and file globs in TOML or YAML.

  • Fastest way to add simple subprocess engines.
  • No Python code for the happy path.
  • Configuration is portable and inspectable.
Cost: quoting, Windows paths, probing, and output discovery become a brittle mini-language.

C. Containers/services

Long-term direction

Give every engine the same HTTP or container entrypoint before integrating it.

  • Strong runtime isolation and reproducibility.
  • Natural path toward distributed execution.
  • Uniform deployment interface.
Deferred: preserve this as an adapter execution mode once the local CLI contract is proven.

Recommended topology

Stable core, replaceable edges

The core understands examples, run records, and comparisons. Only adapters understand engine-specific commands and platform paths.

Example bundle

Inputs and expectations travel together

examples/thinba/
  example.toml
  thinba.key
  thinba.tre
  input.db          # optional
  expected/FVSOut.db

The manifest declares required files, variant, baseline, row keys, excluded metadata, and numeric tolerances.

Engine contract

Probe, validate, run, collect

  1. Probe runtime and version
  2. Validate example compatibility
  3. Build argv without a shell
  4. Run with timeout in isolated workspace
  5. Return structured artifacts and diagnostics

No engine adapter decides whether scientific results pass; comparison remains a separate DuckDB-backed service.

Scope boundary

First delivery

Serial CLI, engine discovery, named examples, isolated workspaces, FVSjl and native executable adapters, DuckDB database comparison, deterministic tests, Make targets, and CI that exercises fake engines plus DB comparison.

Designed now, implemented later

Windows rFVS live adapter qualification, container-backed adapters, remote execution, parallel scheduling, checkpoints, state mutation, and performance benchmarks. Containers remain the intended route toward orchestrating many isolated instances.

Decision recorded

Implement Architecture A: typed Python engine adapters behind a stable run contract. Keep Architecture C visible as the future execution strategy for isolated and parallel engine instances, without adding container machinery to this repository's first milestone.
